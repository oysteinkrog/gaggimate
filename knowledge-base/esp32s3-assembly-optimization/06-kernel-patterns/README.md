# 06-kernel-patterns: bucket index

The shapes a hot loop takes on this chip, and the arithmetic inside it.
Number formats and the multiply, round and saturate sequences that go with
them; getting a value out of a table and a 16-bit pixel built once it is
out; the loop that holds all of it, and the calls around the loop; and the
one large body of vendor-written ESP32-S3 assembly available to read.

Nothing here is a cycle count. These leaves give code shape, instruction
semantics and instruction counts, all of which are claims about what the
compiler emits or what an instruction does. Turning a shape into a time
needs [05-measurement/](../05-measurement/README.md). The instruction facts
the leaves lean on live in [01-scalar-isa/](../01-scalar-isa/README.md) and
[02-pie-vector/](../02-pie-vector/README.md), the placement facts in
[03-memory-hierarchy/](../03-memory-hierarchy/README.md), and what GCC 14
does with any of it in
[04-toolchain-and-codegen/](../04-toolchain-and-codegen/README.md).

| [fixed-point-arithmetic-on-lx7.md](./fixed-point-arithmetic-on-lx7.md) | Choosing a format, the multiply instructions, rounding, saturation, division-free arithmetic, phase accumulators, incremental evaluation, converting at the boundary, and the PIE fixed-point rules | The ESP32-S3 configures every integer option these patterns need, and divide is a setup instruction only, because the ISA manual declares the algorithm implementation-dependent. Which multiply you need follows from where the binary point sits: `MUL16S` plus `SRAI` when the product fits 32 bits, `MULSH` alone when the shift lands at the register boundary, and `MULL`/`MULSH`/`SSAI`/`SRC` when it lands inside the 64-bit product. `Q15 * Q15` overflows for exactly one input pair, `-1.0 * -1.0`. `CLAMPS ar, as, 15` is a one-instruction Q15 clamp that GCC 14.2 never emits, spending four instructions instead. `EE.VMUL.S16` is a complete eight-lane fixed-point multiply with the shift free in `SAR`, but it truncates and does not saturate, and `SAR` is the core's own register, so a loop cannot hold a vector scale there and use a scalar variable shift. PIE dependent-issue distances come from TRM Table 1.7-2; every scalar cycle count is `[uncertain]` because the manual publishes none. |
| [lut-gathers-palettes-and-rgb565.md](./lut-gathers-palettes-and-rgb565.md) | The scalar gather loop, pixel pairs, table sizing and padding, RGB565 layout, the split-channel blend, alpha, ordered dithering, byte order | PIE has no multi-lane gather: `EE.LDXQ.32` loads one 32-bit lane by an index taken from one 16-bit lane, and esp-dsp never uses it. GCC 14.2 compiles a byte-indexed palette lookup to six instructions per pixel, eleven for two interleaved pixels through walked pointers, thirteen for the same two written with an index variable, and twenty for four, keeping the hardware loop in all four. One 32-bit multiply weights all three RGB565 channels at once when the pixel is duplicated into both halves of a word and masked with `0x07E0F81F`; green is the binding field, which caps the weight at 32, and `0x02008010` is the per-field rounding constant. An exhaustive host check over 8.86 billion comparisons per form found zero mismatches against per-channel arithmetic, and the check fails at weight 33 exactly as the headroom argument predicts. LVGL 8.4.0 ships the difference form of the same identity and `(x * 0x8081) >> 23` for the divide by 255, exact to 66298. Ordered dithering must be applied to the full-precision value, before quantisation, or it does nothing. |
| [loop-shapes-scheduling-and-per-call-setup.md](./loop-shapes-scheduling-and-per-call-setup.md) | Twelve rules for the loop and the calls around it: trip counts, call-free bodies, hoisting, incremental stepping, two-way interleave, unrolling, per-call setup, stores, memcpy, branchless selection, loop splitting, and checking the output | State the trip count as one value known before the first iteration, keep the body call-free, and hoist by hand into an `asm` block because GCC's loop-invariant motion pass cannot see inside one. A two-way interleave fills the load-use gap within the 14 usable address registers; a four-way one often spills, and a spilled value reintroduces the stall on the reload. Unrolling here buys scheduling room, not loop overhead, and the 256-byte hardware-loop body cap limits it. `memcpy` on the ESP32-S3 is a call into the boot ROM at `0x400011f4`, not a linked library member: a linker fragment assigns the symbol whenever the target declares `ESP_ROM_HAS_NEWLIB`, and the ROM body is newlib's Xtensa algorithm, a `loopnez` moving 16 bytes with an `SSA8L`/`SRC` misaligned path. A hand loop beats it only for a short constant length, a length and alignment that make the tail handling dead weight, or a throughput need only PIE can meet. |
| [esp-dsp-as-a-reference-kernel-library.md](./esp-dsp-as-a-reference-kernel-library.md) | What Espressif's own DSP library holds, how it dispatches per chip, its assembly conventions, its benchmarks and tests, its licence, and where its patterns stop | Dispatch is a compile-time chain of `#if`/`#define` on `_enabled` macros, `_ansi` last, at zero runtime cost, and the macro names mislead: `dsps_dotprod_s16_aes3_enabled` selects the ESP32 `s16` kernel and the `_aes3` `s8` one. No float kernel in the library is PIE-vectorized: every `q` register belongs to a fixed-point kernel, the float `_aes3` files use only the wide `EE.LDF`/`EE.STF` floating-point load and store with scalar `madd.s` arithmetic, and the `_aes3` biquad uses no extended instruction at all. Kernels state alignment and length preconditions and fall back rather than handle them, either to the ANSI function by `call8` or to the ESP32 body. `v1.8.2` has no PIE convolution on the ESP32-S3. Its own `-O2` benchmarks give 3.0x for the float dot product, 13.1x for the 16-bit FFT and 49.0x for a 64x64 image dot product, whose ESP32 "optimized" path is the same speed as ANSI. The transferable part is the machinery: per-chip dispatch, a documented alignment contract, tests against a portable reference, and benchmarks that state input size and compiler flag. Apache-2.0. |

## Not yet covered

- **A worked cycle budget for one complete pixel loop.** The leaves give instruction counts and dependent-issue distances but never multiply them into a per-row or per-frame time on this chip. The pieces are in [00-foundations/lx7-core-pipeline-and-cost-model.md](../00-foundations/lx7-core-pipeline-and-cost-model.md) and [05-measurement/](../05-measurement/README.md); the arithmetic that joins them belongs in `10-synthesis/`.
- **Row-state builders as a pattern of their own.** The bucket charter names them, and two leaves touch the idea (per-call setup, per-row constant hoisting), but nothing covers what belongs in a builder, how to size it against the pixel loop it feeds, or when caching derived state across calls pays.
- **The vector-index, scalar-lookup design worked end to end.** The LUT leaf names it as one of two designs for a table-driven kernel and gives the alignment rule, but no leaf carries a full example through `EE.VST.128.IP` into a 16-byte-aligned scratch and out through the scalar loop, nor an instruction count to weigh against the fully scalar form.
- **Per-lane conditionals on PIE.** Branchless selection is covered on the scalar side (`MOVEQZ` and the `MIN`/`MAX` family). The vector analogue, building a mask with the `EE.VCMP.*` compares and applying it with `EE.ANDQ`/`EE.ORQ`/`EE.NOTQ`, has no pattern leaf here; the instruction semantics are in [02-pie-vector/pie-arithmetic-multiply-saturate-and-shuffle.md](../02-pie-vector/pie-arithmetic-multiply-saturate-and-shuffle.md).
- **Accumulator kernels: choosing the shift and reading `ACCX` or `QACC` back.** The esp-dsp leaf documents the idioms it found (`wur.accx_*` zero-init, `ee.srs.accx` rounding shift-and-store, `rur.accx_*` raw readout with a manual funnel shift), but there is no leaf on picking the final shift, bounding accumulator growth, or what saturation in the accumulate does to a reference twin.
- **Error-diffusion dithering.** Only ordered dithering is covered. Floyd-Steinberg and its relatives are serial across pixels, which is the interesting fact for this bucket, and no leaf states the trade against the ordered matrix.
- **`memset`, `memmove` and fill patterns.** The loop-shapes leaf analyses `memcpy` only. `memset` and `memmove` are also ROM symbols on this part, and esp-dsp ships a PIE `dsps_memset_aes3.S`, neither of which is compared here.
- **A general table-versus-recompute rule.** The break-even arithmetic is worked only for square root (8 to 10 result bits) and for the sine table against linear interpolation. There is no rule that weighs a table's cache footprint against the instructions it saves, which is the form the question usually takes.
- **Cache blocking for a two-dimensional pass.** Table placement is covered as a ranking question (reads per frame), but nothing covers how to walk a 2D buffer so a table and the working set stay resident together; the miss costs are in [03-memory-hierarchy/caches-sram-psram-and-the-mspi-bus.md](../03-memory-hierarchy/caches-sram-psram-and-the-mspi-bus.md).
- **The distance a kernel must leave between a scalar `WSR.SAR` and the first `EE.VMUL.S16` that reads it.** TRM Table 1.7-2 gives the read stage (1) but covers extended instructions only, so the write stage of the scalar special-register write is unpublished. Flagged `[uncertain]` in the fixed-point leaf; a device or QEMU measurement would settle it.
- **Whether `MUL16S` and `MULL` share a latency on this part.** Unpublished, and it would change the format choice for 16-bit data if they differ. Flagged `[uncertain]` in the fixed-point leaf.
- **Whether an unaligned `S32I` behaves as a plain 32-bit store in every memory region, cached external memory in particular.** The core configuration declares hardware unaligned load and store support and no unaligned exception, which settles the general case; the region-by-region question is flagged `[uncertain]` in the LUT leaf, and the practical advice, align the rows, costs nothing.
- **Whether `EE.LDXQ.32` treats its index lane as signed or unsigned.** The TRM's operation listing does not say. Flagged `[uncertain]` in the LUT leaf; one executed test on the device or in QEMU would settle it.
- **The tie rule for `ROUND.S`.** The ISA manual says "rounding toward the nearest", the `rounds()` helper its operation section uses is defined nowhere in the document, and the FCR rounding mode 0 is named only "round to nearest". Flagged `[uncertain]` in the fixed-point leaf.
- **Why esp-dsp's float FFT wins only 1.8x on the ESP32-S3 where its fixed-point FFT wins 13.1x.** The library does not explain the gap and the esp-dsp leaf's proposed cause is its own inference, tagged `[uncertain]`. The finding that no float kernel there is PIE-vectorized is now recorded and makes the gap less surprising, but it is not a measurement.
